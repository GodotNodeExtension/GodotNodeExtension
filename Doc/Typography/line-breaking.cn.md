# Typography 断行与绕排

一行在哪里结束是一个决策，而排版只做一次：一行提供哪些区间（`LayoutLine.Spans`）、这些区间背后的原因，以及排版
自己放上去的标记（`Hanging`、`HyphenRun`），都会随输出返回，其字段逐一说明见
[`output-format.cn.md`](output-format.cn.md)。本文讲的是这些数字背后的行为：哪些规则否决一个断点、两端对齐的行
怎样要到或让出空间、标记什么时候可以落在行外、长词怎样在词内断开、文字怎样绕开一个形状，以及制表符把它之后的
内容送到哪里。本文提到的请求字段见 [`input-format.cn.md`](input-format.cn.md)，各语言取的值见
[`languages.cn.md`](languages.cn.md)。

## Unicode 决定什么，语言再补什么

两套 Unicode 算法提供了所有语言共用的基线：

- **断行（UAX #14）**回答一个问题——这两个字符之间究竟能不能分开？它的结论是每种语言的默认答案，对西文与右向左
  文本而言它就是全部规则。
- **切分（UAX #29）**提供单位。字形簇不可分，所以一行绝不会在簇内断开（组合标记、CRLF 对、ZWJ emoji 序列，就断行
  而言都不是两个字符）；词边界则是词级规则（断词）的起点。

两套算法在每次改动时都对照 Unicode 自己的符合性测试集，它们据以编译的属性表由一份记录在案的 Unicode 版本生成，
于是版本变更是一次可复核的变更，而不是一次无声的变更。

语言从不重新实现这条基线，只对它做裁剪。**禁则**（kinsoku）就是中日韩约定所加的裁剪：基线可能允许在某两个字符
之间断开，而约定拒绝它出现在行首或行末。语言剖面会指明自己运行哪套规则集——`line-breaking.unicode` 是那条纯基线，
`line-breaking.kinsoku` 是中日韩的禁则——宿主也可以注册自己的规则集并让某个剖面指名引用，于是引擎从未见过的约定
是一次数据变更，而不是框架变更。

每一对相邻簇会变成一个**边界**，在编译期决定一次，之后每一步都复用它。边界携带：这里能不能起一行或结束一行、两个
簇能不能被分开、这里能不能加空间、两簇之间的间隙以及它可被挤压或拉伸的范围、这段间隙归谁，以及一条机器可读的原因。
断行搜索读这些决策，而不是再去问字符分类器——这正是规则只有一个落点的原因：规则住在语言里，断行的阶段与调整的
阶段都只是消费它们。

## 行首与行末禁则

两个请求字段决定禁则是否生效、有多严；两者都可空，`null` 表示“由语言决定”：

| 字段 | 取值 | 决定什么 |
|---|---|---|
| `EnableLineProhibition` | `true`、`false` | 语言的禁则规则究竟跑不跑 |
| `ProhibitionLevel` | `None`、`Basic`、`Gb`、`Strict` | 禁则有多严——影响哪些字符类 |

| 级别 | 拒绝什么 |
|---|---|
| `None` | 什么都不拒绝：文字在 Unicode 基线允许的地方断开 |
| `Basic` | 类集的基本档：停顿与句末标点、后引号类、连接符、间隔号与斜线不得作行首，前引号类不得作行末 |
| `Gb` | 同一套类集的 GB/T 15834 形态；对中文而言它在行末补上斜线，而日文与韩文类集在这一档定义与 `Basic` 相同的字符 |
| `Strict` | 最严档：基本档之外，双字宽的破折号与省略号也不得作行首 |

**哪些字符算数属于语言数据，而不属于算法。** 规则始终是同一条——“不要用后引号起一行”——不同的是类集与严苛程度。
随引擎提供的类集有：引擎的历史集合、中文（clreq §6.1.1：停顿与句末标点、后引号类、连接符、间隔号与斜线不得作行首，
前引号类不得作行末）、日文（jlreq §3.1.7/§3.9：后括号、连字符、分隔号、中点、句点、逗号、叠字记号、长音符与小假名
不得作行首，前括号不得作行末——即 jlreq 的 `cl-01`…`cl-30` 中与行边缘有关的那几行）以及韩文（klreq §7.1.2/§7.1.3
自己的集合）。宿主以同样的形状注册自己的类集：每一档严苛程度各有一套行首集与行末集。

**更严的一侧胜出。** 只要有一侧的约定拒绝这一对，它就被拒绝：禁则一旦有一侧声明，它就是禁则，绝不会被当作偏好去
与另一侧的沉默折中。

**有些对根本不能分开**，与宽度无关：双字宽破折号的两半、省略号的两半、数字与它的前后缀、单位或货币符号、带注音的
文本段（注音绝不会与它注的字分开）、制表符与在制表位对齐的内容，以及零宽的动作标记与它后面的内容。这些到达断行
搜索时只表现为“这两簇必须留在同一行”，所以搜索本身不需要知道原因。

当一行用尽空间又没有任何候选时，它只能在必须断开的位置断开：一个装不下任何不可拆文本段的盒子，或一段每个断点都
被拒绝的文字，会让一行短于它的宽度，或让一个片段溢出。这是排版质量的信号而不是正常结果，而
`LayoutResult.ProhibitedBreakSkips` 统计了被禁则否决的候选数，这正是“这一行远没排满就换行了”最省力的解释。

## 挤压与拉伸一行

两端对齐要求段落中除最后一行之外的每一行都填满分给它的空间，而一行可以朝两个方向动。下面两张表的次序就是全部
策略：一行先从最能让出空间的地方取，再还给最能接收空间的地方。

**一行按这个次序获得空间：**

| 优先级 | 空间从哪来 | 上界 |
|---|---|---|
| 1 | 西文文本的词间距 | 规范未给出——西文段落的弹性就在这里 |
| 2 | 中日韩文本与西文之间的间隙 | 约定给出的上界（见下） |
| 3 | 两个中日韩字符之间的字间距 | 规范未给出 |

**一行按这个次序让出空间：**

| 优先级 | 空间从哪来 | 下界 |
|---|---|---|
| 1 | 结束一行的那个标点 | 压到半字宽，且只在语言允许剪的时候（见下） |
| 2 | 西文文本的词间距 | 每个空格有上限，且那是引擎取值而不是规范给出的数字 |
| 3 | 中日韩文本与西文之间的间隙 | 约定给出的下界（见下） |
| 4 | 行上其余的标点 | 每个标记按比例压缩，至多压掉自身宽度的一半 |

挤压的第一优先级是语言决策，不是引擎决策。中文在需要空间时剪掉行末全角标点尾部半个字宽（clreq §6.2.2.3）；日文
保留句点之后那半个字宽、不许压缩，因为那半个字宽是标点自身的一部分，所以日文一行装不下时改为更早换行
（jlreq §3.1.9）；韩文早已为横排的句读选了更窄的字形，那是一次显示形态替换而不是宽度规则。
`EnablePunctuationCompression` 可以整体关掉挤压中与标点有关的那一半，供“宁可换行也不让标点让宽”的调用方使用。

**唯一由约定给出范围的间隙**是中日韩文本与西文之间的间隙：默认四分之一个字宽（clreq §6.3.3、jlreq §3.2.6），可压
至八分之一字宽、可拉至半个字宽。当中日韩与西文直接相邻而原本没有间隙时，排版会插入这段间隙——
`EnableCjkLatinSpacing` 决定是否插入，`CjkLatinSpacingEm` 决定它有多宽。

| 边界 | 谁消费它 | 用尽时怎样 |
|---|---|---|
| 1/8 em——下界 | 挤压 | 间隙不再让出空间，挤压继续用下一个优先级 |
| 1/4 em——默认值 | —— | 排版在两种文字之间插入的空间 |
| 1/2 em——上界 | 拉伸 | 间隙不再变宽，剩余的松弛交给下一个优先级 |

因此两端都被消费，也都不会被越界：两端对齐的行不会把间隙拉过约定允许的宽度，而是改从中日韩文本的字间距里取；被
挤压的行不会把间隙压过同一约定的下限，而是把它压到下限为止。这是唯一从约定读取范围的间隙；其余各类间隙都由调整
阶段按自己的优先级处理，没有规范给出的范围。

约定不允许进一步分开的一对——分離禁止，jlreq §3.1.11——根本不是拉伸候选，无论这一行多想要它的空间。

有两种情形是刻意不拉伸的：**段落的最后一行**，它在哪里结束就在哪里结束；以及**提供多于一个区间的行**，它按区间
各自左对齐——跨越实际上是并排两行的间隙去分配空间是另一个问题，假装它不存在会把文字搬到中间的障碍物上。一行
的亏空或松弛不足半个像素时，它保持在自己的自然位置上，因为四舍五入级别的差异不该让字形移动。

## 悬挂标点

不得起一行的标记不必真的移到下一行：在约定允许时，它留在当前行的行末，并伸出行边缘——这就是 clreq §6.1.3 的
悬挂标点、jlreq 的ぶら下げ。这一行随后就此结束，它之后的东西起下一行，于是这一行的内容比分配给它的区间宽出一个
标记。这个超出量正是该行为的目的而不是意外：内容尺寸把它算进去，消费者把它画在行盒之外。

一个标记要悬挂，需要三件事一致：

- **标记本身**必须是语言拒绝其作行首的字符——停顿与句末标点、后引号类或省略号；普通字符没有可挂之处；
- **语言**必须允许悬挂；
- **这一行**在语言拒绝混排悬挂时，必须还没有西文字（jlreq §3.8.2 认为悬挂标记与西文并排读起来不好）。

| 语言 | 悬挂标点 | 原因 |
|---|---|---|
| 简体中文 | 允许（clreq §6.1.3） | 正是提出该做法的约定 |
| 繁体中文 | 仅竖排（clreq §6.1.3） | 于是横排下该标记像其它字符一样移到下一行 |
| 日文 | 混排时不可（jlreq §3.8.2） | 已经带了西文字母的行拒绝该标记 |
| 韩文 | 不启用 | 没有随引擎提供的韩文约定要求它 |
| 西文与右向左文本 | 不适用 | 没有禁则的语言没有“不得作行首”的标记可挂 |

提供多于一个区间的行永远不会悬挂标记，因为它第一个区间的末端就是排除区的边缘：挂在那里的标记会被印在障碍物上。
元素用 `Hanging = true` 报告结果，而排版确实把它放在了区间边缘之外，所以消费者画在那里、不要裁回。

## 在词内断开

窄栏里的长词不必溢出整行，也不必在它之前留下空档：对随引擎提供断词模式的语言，排版会在语言允许的位置切开这个词
并就此断行。

| 语言标签 | 模式 |
|---|---|
| `en` | 美式英语 |
| `en-GB` | 英式英语 |
| `de` | 德语 1996 正字法 |
| `fr` | 法语 |

模式取自 hyph-utf8 的 TeX 模式，每张表都记录自己的来源、版本、校验和与许可。`EnableHyphenation` 可按请求关掉该
行为；`null` 交给语言决定。没有模式的语言不受影响；约定本身只在字符之间或词边界断开、从不加连字符的语言也一样
不受影响——中文、日文与韩文都不带模式，因为词级断开并不是它们约定里的规则。

**这个断点怎样变成一个普通断点。** 编译期会把一段字母组成的词（至少四个字符，不含数字、连字符或斜线，且未被显示
形态替换改写）在语言允许的位置切开。每个片段变成一个段，其后带有断行机会；这与 Unicode 算法为标点和连字符产生的
形状相同，于是断行搜索完全不需要认识词：它只看到词内一个合法断点，行需要时就取它。可能结束一行的片段会预留连字符的
前进量——连字符在整个词上只塑形一次，就在编译期——所以装填判定会为它付费，而断行器最终没有断开的词，也不会因为
一个它没用到的连字符宽度而变窄。

**连字符本身从哪来。** 由行装配阶段放置，作为一个合成元素，其 `Reason` 为 `HyphenationBreak`：空的源区间、没有簇，
字形是编译期塑形好的那一段（断开的片段以 `HyphenRun` 报告它）。消费者画拿到手的连字符，绝不自己补一个，因为需要
自己补的渲染器就得知道断词这回事——而编译期塑形的一切意义就在于没有别人需要知道。

**作者自己写的软连字符（U+00AD）**不需要模式：该字符的 Unicode 断行类别本来就允许在它之后断开，所以排版免费得到
一个合法断点。在这类断点处排版不会自己补连字符：字符是调用方写的，画出来的就是调用方写的东西。

## 绕排与绕排形状

绕排区是文字绕开的一个有位置的排除区——一张图、一条线、一个自定义区域——请求的 `WrapRegions` 列表就是告诉排版它
在哪里的地方。一个绕排区给出一个**形状**、它在内容空间的**位置**、文字与它保持的**外边距**，以及它属于哪些行
（`FirstLine`/`LastLine`，`-1` 表示“到排版结束”）。形状是该是矩形时就是矩形，否则是多边形；多边形自带逐扫描线的
区间表，或由顶点按奇偶规则构造而成，后者正是让凹形在中间收窄的原因。

**一行会问形状在这一行自己的 Y 上占哪里**——行高会计入，所以从一行中途才开始的形状仍然遮住这一行——然后在内容宽度
内取补集，得出自己有哪些空间。这正是 `LayoutLine.Spans` 报告的东西，而一行可能有一个区间或多个：

- **一个区间**：普通行；
- **两个或更多**：排除区只遮住行的一部分时——左浮动与右浮动并存会在中间留下一个区间，中间比两侧窄的形状会在两侧
  各留下一个；
- **没有区间**：形状遮住整行时，排版会前进到躲开该排除区的第一个块向坐标，在那里排这一行。

笔位走到一个区间的末端时，会继续进入下一个区间，而不是提前结束这一行：一行有多少空间就有多满，而在障碍物边缘断开
会让这一行剩下的部分空着。`LineLeft` 与 `LineRight` 只描述**第一个**区间，所以任何定位元素的代码都必须使用元素被
放进的那个区间——`LayoutElement.SpanIndex` 指明了是哪一个，把落在第二个区间的元素按第一个区间摆，会把文字搬到
障碍物上。

段落缩进收窄的是整行的外侧边缘，而不是每个区间：左缩进从第一个区间的起点扣掉，右缩进从最后一个区间的末端扣掉，
所以一行中间的排除区永远不会给它右侧的内容加缩进。

尚未建模的：**浮动的生命周期**（形状在行与行之间移动或改变大小，而不是事先声明它属于哪些行）、第二个轮廓造成的
**洞**，以及**自交轮廓**意味着什么——奇偶规则让它交替填充而不是填满，那是与洞不同的另一个形状。

## 制表位与引导字符

制表符是一条对齐指令，不是自带宽度的字符：它没有墨迹来决定间隙有多宽，所以排版必须被告知制表符把它后面的内容送到
哪里。`TabStops` 是作者给出的制表位列表——相对内容原点的位置，按升序——每个制表位说明内容在那里怎样对齐：

| `TabAlignment` | 在制表位处发生什么 |
|---|---|
| `Left`（默认） | 内容从制表位开始 |
| `Center` | 内容以制表位为中心 |
| `Right` | 内容在制表位结束 |
| `DecimalPoint` | 内容的小数点位于制表位，一列数字就是这样对齐的；没有小数点的内容退回 `Left` |

制表符把它后面的内容送到**笔位之后的第一个制表位**。过了最后一个制表位之后由自动制表位接手：`DefaultTabStopEm`
（默认四个字宽）从这一行自己的起点起算，字宽取这一行所用字号。自动制表位关掉时，过了最后一个制表位的制表符什么也
不做——正该如此。

**引导字符是记录下来的，不是塑形出来的。** 排版不会用字形去填这段间隙；它只说明该处属于哪个字符、间隙有多宽。
制表符自己的元素把引导字符放在 `Text` 里（作者没要求时为空），把到制表位的间隙放在宽度里，于是消费者在这段间隙里
重复该字符即可，无需塑形任何东西——目录里的那些点对排版不花任何代价。

制表符绑定它之后的内容：一行不得在制表符与在它的制表位对齐的内容之间断开，所以表头与表元会留在一起。

在定位上，制表位有最后发言权：它们在按区间对齐完成之后、也在网格发过言之后才应用，因为制表位是作者指定的位置，而
网格是全局规则，只有当两者同时启用时才会彼此冲突。被断开的词末尾那个连字符，连制表位之后才放。

```csharp
using GodotNodeExtension.Component.Typography.Core.Model;

// 普通行提供一个区间，文字绕开排除区时会多于一个；每个元素都会报告它落在哪个区间。
static LineSpan IntervalOf(LayoutLine line, in LayoutElement element)
{
    LineSpan[] spans = line.Spans.Length > 0 ? line.Spans : [new LineSpan(line.LineLeft, line.LineRight)];
    return spans[element.SpanIndex];
}

// 悬挂的标记就是排版放在行边缘之外的普通文字：画在那里，不要裁回。
static bool DrawsOutsideTheLine(in LayoutElement element) => element.Hanging;
```
