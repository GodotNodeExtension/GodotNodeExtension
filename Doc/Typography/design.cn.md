# Typography 设计

本文讲的是这条排版流水线**为什么**是这样切分的：它分成哪两个阶段、一次排版由哪四个对象承载、其余设计由哪
四条原则推出，以及唯一那条让"一行"可以不朝右跑的抽象。它是设计文档而不是操作步骤——调用方提交什么字段、
渲染器收到什么字段，真相在 [`input-format.cn.md`](input-format.cn.md) 与
[`output-format.cn.md`](output-format.cn.md)；书写模式在取值层面改变了什么，见
[`writing-modes.cn.md`](writing-modes.cn.md)。以下示例使用本组件的命名空间：

```csharp
using Godot;
using GodotNodeExtension.Component.Typography.Core;         // TypographyFeatureRegistry
using GodotNodeExtension.Component.Typography.Core.Model;   // WritingMode, TextAlignment, LayoutAxes
using GodotNodeExtension.Component.Typography.Languages;    // LanguageProfile, LanguageProfileRegistry, TypographyParameters
```

## 两个阶段

流水线在"宽度进来的地方"切开。只靠文字、样式与已解析语言就能定下来的部分属于**编译期**；需要盒子、对齐与
排除区的部分属于**执行期**。

- **编译期**——每个段落跑一次，与宽度无关，结果可缓存。它的产物是*已准备好的段落*：run、带字符属性的
  cluster、边界数组，以及已塑形的字形。
- **执行期**——每次排版跑一次，与宽度有关，重排重跑的就是它。它的产物是输出：带区间的行、已定位的元素、
  字形 run、背景、注音与着重号。

这条切分不是实现细节，而是请求类型背后的契约。只改宽度的请求复用已准备好的段落，结果会把与宽度无关的那一半
单独报成一项耗时（`Timings.CompileMs`），在这种重排中它必须是零。同一条切分也让"改一条规则"可复核：规则在
编译期生效，因此改规则不可能悄悄推翻执行期自己作出的断行决定。

### 各阶段负责什么

| 阶段 | 所属 | 决定什么 | 产物 |
|---|---|---|---|
| `S1` 切 run | 编译期 | 文本分成哪些 run、各自属于哪种语言与方向、其中哪些是原子的 | 带脚本、语言、方向与源区间的 run |
| `S2` 归簇 | 编译期 | 最小不可分单位是什么、每个单位被归为哪一类、两个相邻单位之间适用什么决定 | 带字符类与源区间的 cluster，以及边界数组 |
| `S3` 测量 | 编译期 | 文字在字符层面长什么样：用哪个字面、哪些字形、多宽 | 带 advance 与 offset 的已塑形字形、cluster 到字形的映射、字体决策 |
| `S4` 断行 | 执行期 | 在给定宽度与排除区下，一行可以在哪里结束 | 行：每行拥有哪些 cluster、以及它提供哪些区间 |
| `S5` 行调整 | 执行期 | 一行内部的余量怎么用：挤压、拉伸、对齐、缩进 | 调整后的位置，以及实际施加的量 |
| `S6` 装配 | 执行期 | 这次排版最终变成哪些元素：文字、背景、注音、着重号、装饰 | 输出元素流，每个元素带着自己的几何与原因 |

```text
调用方的元素流
        │
        ├── 编译期  （每段落一次，与宽度无关，可缓存）
        │     S1 切 run   run：脚本、语言、方向、源区间
        │     S2 归簇     字素簇、字符属性、边界
        │     S3 测量     塑形：glyph id、advance、cluster 映射
        │
        └── 执行期  （每次排版一次，与宽度有关）
              S4 断行     边界决策变成行
              S5 调整     间距、挤压/拉伸、对齐、缩进
              S6 装配     字形 run、背景、注音、着重号
        │
渲染器要画的这次排版
```

## 四个模型

一次排版由四个对象承载，每一个回答的问题都不同。把它们分开，正是让其中一个改变时不必重新推导另外几个的
原因。

### 元素流：调用方表达什么

输入是一串语义元素：说的是什么（文字）、应该长什么样（字体、字号、装饰）、它是一处注音而不是一行正文，以及
它携带的是动作、扩展区还是非文字盒子。它还携带每个段落一个语言提示，因为段落是语言能挂上的最小单位。

几何是刻意不在其中的。处于正常流中的元素，其 `Position` 会被忽略——位置归排版所有；而排版回写的那些字段
（基线、源区间、字形 run、原因）在输入方向上没有意义：生产方把它们填上也不会改变任何结果，这正是"半成品元素
不会被误当成输入"的原因。这条元素流在 [`input-format.cn.md`](input-format.cn.md) 里逐字段描述。

### 边界：规则在两个 cluster 之间决定了什么

每一对相邻 cluster 产生一个 `Boundary`：一个决策点，把断行搜索与调整阶段需要知道关于这一对的一切收在一处。
它说明接触的种类（普通相邻、空格、脚本切换、标点、带单位的数字、行内对象、硬换行）、两侧各自的脚本角色、
这里若有调整归哪一侧所有、自然间距以及可压缩可拉伸的区间，还有四条禁止——此处不可断、右侧不可起行、左侧
不可收行、不可拉伸。它带有机器可读的 `Reason`，因此一次排版的转储可以自解释；还带一个派生字段 `IsNotable`，
把占多数的普通相邻过滤掉。

边界是编译期的产物，按这一对的左侧 cluster 索引，且与宽度无关。它们**不属于**结果：结果只报告构建边界的
耗时与被否决的断点数量，不报告其内容。消费者永远不读边界来绘制——那等于从字符类反推语言规则，而这正是这套
模型要消除的事。

### 行与区间：文字可以站在哪里

一行是沿块向轴的一个盒子，它有多高取决于它承载了什么：注音带、着重号、下划线或超出基字的注音列所需的余地
都被加进去（`ExtraAbove` 与 `ExtraBelow` 分列块起始侧与块结束侧），因此同一行上的基线会一起移动，即便请求
没有声明行距，相邻两行也不会重叠。`Ascent` 与 `Descent` 是该行元素沿这条轴的最大值。

一行提供的是**多个区间**而不是一条跨度：只遮住一行一部分的排除区会把这行两侧的可用余量都留下，文字继续往前
流。`LineSpan` 是区间的类型，`LineLeft`/`LineRight` 只是询问第一个区间的便捷方式，而元素会报告自己落在哪个
区间（`SpanIndex`）——按行的第一个区间去定位元素，会把第二个区间的文字画到第一个区间里面。`LineIndent` 是
第一个区间的内容相对 `LineLeft` 额外推入的偏移量。

### 字形：画什么

输出是一串扁平、已定位的元素，每个元素带着自己要画的已塑形字形（`GlyphRun`）、所在行给它的基线、它覆盖的源
文字、它持有的 cluster，以及它的几何为何如此的原因。注音与着重号自带几何与自己的字形，因此它们同样不会被
测量两次。回映到文字走源区间与 cluster 区间，永远不走元素顺序：一个源元素会变成许多输出元素，而从右到左的
文字或块自身的子排版会改变它们的先后。[`output-format.cn.md`](output-format.cn.md) 是这些字段的契约。

## 边界是决策，不是间隙

保存字间隙最直觉的地方是字符本身：把标点量得宽一点，让排版其余部分去适应。可这个模型说不出读者真正需要知道
的事——句点之后的间隙属于句点还是属于它后面的那个字、一行在这里究竟能不能断、这一行只差一个字时这个间隙能
不能压、能不能拉。

所以这段空隙不挂靠任何一侧，而是它们**之间**的一个决策。这也正是调整阶段得以成立的原因：有归属的间隙可以
被度量和移动，带区间（`MinSpacing`/`MaxSpacing`）的间隙能压到下限、拉到上限而不越过，禁止则是位置的属性
而不是字符的属性，因此同一个字符可以在这里允许收行、在那里拒绝。它同时让规则只存在于一处：断行搜索遍历候选
点、读取决策，不再回头去问分类器自己看的是什么；于是增删一条规则是编译期的改动，也不会在两个消费边界的阶段
之间漂移。

## 语言是剖面，不是代码路径

语言不是引擎里的一个分支，而是一份 `LanguageProfile`：一组参数（禁则的严格程度与所用类集、是否启用脚本间距
及其区间、首行缩进、默认对齐、显示形态如何替换源字符、注音在哪一侧、朝哪个方向读、着重号在哪一侧），加上它
想要的那些规则特性的 id。解析是一次标签查找：从最具体的标签逐级退到最不具体的，终点是"不做任何语言假设"的
那份剖面，而绝不会退回到没人要求过的某种语言。

由此得到的后果正是这套设计的目的：

- **语言包是数据。** 新增一种语言就是新增一份剖面（最多再加一套引擎没见过的规则）。框架被要求守住的验收
  判据就是这一条：*新增一种语言不得需要改动框架*。
- **剖面在注册时就校验，而不是在被使用时才暴露。** 一份剖面若指名了没人注册的规则、引擎找不到的类集，或
  自相矛盾的组合，就在那一刻大声失败，而不是悄悄用兜底规则把文字排出去。
- **请求始终优先。** 剖面为"受语言治理的那一半"提供默认值；调用方显式给出的取值都叠加在其上，因此剖面
  不可能覆盖一个刻意的选择。
- **粒度是段落。** 几何（盒子、内边距、排除区）属于请求，因为段落并不拥有它所处的盒子；受语言治理的那一半
  属于段落——这就是同一份文档可以引用另一种语言、而每个段落各按自己的规范排的原因。

```csharp compile
// A language is a set of values plus the ids of the rules it wants - no algorithm of its own.
LanguageProfileRegistry.Shared.Register(new LanguageProfile(
    id: "nl",
    fallback: ["und"],
    parameters: new TypographyParameters
    {
        WritingMode = WritingMode.HorizontalTb,
        BoundaryRuleFeature = TypographyFeatureRegistry.UnicodeBoundaryRuleId,
        EnableLineProhibition = false,
        EnableCjkLatinSpacing = false,
        FirstLineIndent = 0,
        Alignment = TextAlignment.Left,
    },
    description: "Dutch: the Unicode baseline, no prohibition, no script spacing"));
```

## 规则差异是特性

两种语言的区别很少是"有这条规则／没有这条规则"，而是**哪一条**规则；而且宿主可能需要引擎从未听说过的规则。
所以规则集是注册进来的特性而不是分支：一个特性声明自己的 id、它负责的作用域（段落、run、边界、cluster）、
它依赖什么、与什么冲突；引擎自带两条边界规则——Unicode 断行算法，以及在其之上裁剪出的 CJK 禁则。剖面指名
它要的 id，而断行搜索并不知道自己拿到的是哪一条。

注册就是校验组合的地方。一份剖面若其特性依赖了该剖面并未包含的东西，或其特性之间声明了冲突，就在那时被拒绝
并给出原因——坏掉的语言包大声失败，而不是悄悄改做别的事。同一套机制也是宿主扩展引擎的方式：实现这个特性、
注册它、让剖面指名它。

## 行有多个区间

绕着图片流的文字不只是变窄：中间收窄的形状会在一行的**两侧**都留下可用空间。用一对左右边界来建模的行表达不了
这件事，定位元素的阶段也无从知道一行第二段的起点在哪里。

所以一行提供的是一串有序、互不重叠、且穷尽的区间，元素说明自己被放在哪个区间，而每个区间的对齐基准是它自己的
（把空白摊到"其实是两行"的间隙上，是另一个问题，本模型并不声称解决它）。行几何的其余部分与从前一样：第一个
区间是常见情形，询问它仍然只是一行代码。

## 轴抽象：inline、block 与书写模式

书写模式只决定两件事，别无其他：一行朝哪个方向跑（**inline** 轴），以及行朝哪个方向推进（**block** 轴）。
横排是行向右增长、行向下堆叠；从右到左的竖排是行向下增长、列向左推进。若把它建模成每个阶段内部的"X 还是
Y"，那每一处算坐标的地方都会多一个分支，而每新增一种模式又会把它们乘一遍。

因此每个阶段都用 inline 与 block 两个标量表达几何，映射进内容空间只发生在一处。`LayoutAxes` 就是那一处：
它知道 inline 单位向量、block 单位向量、块坐标零点在哪里（内容框的块起始缘——从右到左的列就是它的**右**
缘），以及如何把一对标量变成点、把内容空间的向量变成 inline 或 block 坐标、把一对跨度变成盒子尺寸。内容空间
本身始终不变：X 仍向右、Y 仍向下，于是排除区、命中测试、内边距与滚动偏移都继续按页面坐标工作，一种书写模式
只是表里的一行，而不是第二套几何。

```csharp compile
// Inline/block scalars in, content space out: no stage has to ask which mode it is in.
var axes = new LayoutAxes(WritingMode.VerticalRl, BlockExtentLimit: 800f);

Vector2 boxStart = axes.Point(inlinePos: 0f, blockPos: 0f);    // block coordinate 0 at the box' top: its right corner
Vector2 boxSize = axes.Size(inlineExtent: 160f, blockExtent: 24f);
float baseline = axes.Block(boxStart) + 12f;                   // a block-axis coordinate, not a Y
```

有两个输出字段继承了这条抽象，而两者都容易按老方式去读：基线是块向轴上的坐标而不是一个 Y，已排版盒子的尺寸
先是块向跨度、后是行内跨度。书写模式对应用可见取值的影响，见 [`writing-modes.cn.md`](writing-modes.cn.md)。

## 为什么测量不交给渲染器

文本引擎可以把字符串交给渲染器，让它自己塑形、测量、绘制。但那也会重新引入这套设计要消除的失败：排版是用
**它**量出的 advance 来断行的，而渲染器里的第二次塑形就是关于同一段文字的第二个意见。不同的字体解析、不同的
特性集合、引擎看不到的某个字体——任何一个都会改变画出来的宽度，于是按测量刚好放下的那一行会压到邻行，或者
差一截到不了页边。这种分歧是无声的，而且偏偏出现在字体变化的时候——而那正是文档绝不能自己重排的时刻。

所以测量不外派：编译期只塑形一次，输出把结果直接带上——glyph id、它们的 advance 与 offset、各自属于哪个
字面、各自来自哪个 cluster。绘制于是只剩平移，这也是为什么渲染器在字形这条路径上完全不需要字体度量，以及
为什么换字体不会移动一行。同一条规则也覆盖了渲染器本来得自己编出来的东西：自动断词处的连字符在编译期塑形、
执行期只负责摆放；注音与着重号带着自己的字形与几何一起到达；显示形态在塑形之前就已经替换，因此画出来的字形
就是被测量过的那些。

这条性质由不变量强制，而不是靠自觉：每个 cluster 最多到达输出一次，源文本被恰好覆盖一次，字形 advance 之和
等于测量宽度，且只有文字元素携带字形 run。仍然自己塑形字符串的渲染器无法满足最后一条，而这正是重点。

## 两份格式文档在流水线上的位置

流水线有两个端，每个端各有一份在那个端上为真的文档。

| 文档 | 讲的是 | 何时读 |
|---|---|---|
| [`input-format.cn.md`](input-format.cn.md) | 调用方提交的元素流与请求设置：类型、单位、默认值、哨兵值，以及每个取值必须满足什么 | 构建请求时，以及编译期——它消费的正是这些字段 |
| [`output-format.cn.md`](output-format.cn.md) | 回传的元素流、行、字形、注音与边界结构，逐字段说明，并给出消费者对每个字段必须遵守的规则 | 结果到达之后、在绘制、回映或命中测试之前 |
| 本文 | 流水线为何这样切分，以及对它的改动必须守住什么 | 需要做决定的时候：新增一种语言、一条规则、一种模式，或一个消费者 |

[`writing-modes.cn.md`](writing-modes.cn.md) 是第四块：所选的书写模式改变了这两份契约所描述的几何中的什么。
三者刻意互不重复——字段级的真相在那两份格式文档里，本文解释它们所描述的形状。
