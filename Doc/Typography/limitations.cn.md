# Typography 局限

没有任何排版引擎实现了全部约定，而对"差出来的那部分"唯一诚实的处理方式就是把它写下来。本页就是这份记录：
本组件不做什么、改用什么代替、以及在有的情况下怎么绕过去。每一条都是决策，不是缺陷，所以你在输出里遇到的
行为就是这里写明的行为。

## 断行与挤压

- **自动断词。** *现在*：在附带词表的语言（`en`、`en-GB`、`de`、`fr`）里，窄栏中的长词会在自己内部断开，而
  `EnableHyphenation` 可以按请求关掉这一行为。可能断词的词在度量时就把连字符的推进量预留出来，真的在该处断开
  的行以行装配阶段放下的连字符结尾；它的字形在编译阶段就塑形好了，所以渲染器依然只画它收到的东西。*缺什么*：
  没有词表的语言完全不断词。*绕过办法*：作者自己写的软连字符（U+00AD）在任何语言里都能让词在你放的位置断开。
- **被绕排切成两段的行的两端对齐。** *现在*：被切成两个区间的行退回按区间左对齐。*缺什么*：把多余的空间分配到
  本质上是一整行的各个间隙上，所以这样的行不会两端对齐。*绕过办法*：把带绕排的段落整体设为左对齐，这样一个块
  里不会混着两种对齐行为。
- **悬挂标点。** *现在*：在约定允许的地方已经实现——本该落在下一行行首的标记会留在当前行末尾并探出行的边缘
  （clreq §6.1.3 允许简体中文这样做；繁体中文只在竖排下可用；jlreq §3.8.2 在混排中不允许）。内容尺寸会把这段
  探出的部分计算在内，这本来就是悬挂标点的含义，元素会报出 `Reason=HangingPunctuation`。*缺什么*：这些规则以内
  没有缺的——约定不允许悬挂的语言就得不到悬挂。
- **行首开括号那半格空白。** *现在*：语言要求修剪时就修剪（jlreq §3.1.5 的折り返し天付き、clreq §6.3.2.3；
  韩文没有这类调整）：该行多出半 em，元素的 `Reason` 为 `OpeningBracketHalfWidth`。*缺什么*：约定没有提出的
  调整不会被发明出来，所以表示不需要调整的语言保留开括号完整的半格。
- **间隙的可压缩区间。** *现在*：中西文间隙两边都带着界限（clreq §6.3.3、jlreq §3.2.6：1/8 到 1/2 em），而且
  两端都会被用到——拉伸停在上界，挤压停在下界。*缺什么*：其它各类间隙的区间并不从边界上读取；那些间隙由调整
  阶段按它自己的优先级处理，而那些优先级是引擎的取值，不是约定给出的数字。

## 绕排

- **排除区域。** *现在*：矩形可用，逐渐收窄的多边形也可用：一个形状可以占据同一行上的多个区间，文字因而能在它
  两侧流动，每个元素都会报出自己落在哪个区间（`SpanIndex`）。*缺什么*：浮动体的生命周期（形状在行与行之间移动
  或改变大小）、来自第二条轮廓的洞，以及自交轮廓到底是什么含义——奇偶规则让它在填充与挖空之间交替。*绕过办法*：
  给移动形状的每一种状态各自的行范围（`WrapRegion.FirstLine`/`LastLine`），并为该状态重新排一次这一段。

## 注音

- **Mono、Group 与 Jukugo。** *现在*：三种都已落地；注文按调用方要求的比例塑形（`RubySpec.SizeRatio`，默认是
  基文字号的一半），被注音的文本段永不跨行断开，它落在哪里、朝哪个方向读，由语言决定。熟语注音在某个字的注文比
  该字本身宽时，会加大基文段的字间距，让相邻注文互不相撞（jlreq §3.3.7）。*缺什么*：这个加宽每个间隙的上限是
  引擎取值，因为约定给出的是原则而不是数字。
- **注音需要的空间由引擎自己留。** *现在*：注音带由排版预留，并计入行自身的盒，于是被注音的行会长高，而不会让
  注文压到上一行——即使作者一点行距都没给。旁注式注音的字列超出量（每个被注音的字半个基文字号，clreq §5.5.3.2）
  同样让行变高。*缺什么*：这是对约定的刻意偏离。jlreq 把注音带留给作者的行距，clreq 则要求竖排右注的行间隙为
  基文字号的一倍半；两者都不会去排一份作者什么都没给的文档。引擎自己预留了这条带，而不是假设作者留了。
- **尺寸比例，以及那半格留给谁。** *现在*：注文默认取基文字号的一半（jlreq 的取值，也是 CSS Ruby 的 UA 样式表
  给每个注文的值）；注音的方向是它自己的——`Vertical` 让它沿自己的一列向下排，一个符号接一个符号，紧贴基字，
  在横排段落里也一样（clreq §5.5.3.1）；它的空间按字形真正留下的墨迹度量，而不是按注文字体的行度量，所以这条带
  永远不会比它为之存在的那个符号更短。*缺什么*：clreq §5.5.3.2 的 3:10 比例不由引擎强制，那个数字属于需要它的
  那套注音体系；而且旁注式注音占的那半格只加在被注音的字上，没有加在未被注音的字上——同一条注在横排段落里要求
  的正是后者（引擎实现的是这条目的的最小读法）。*绕过办法*：自己要求想要的比例——注音符号用
  `SizeRatio = 0.3f`。

## 着重号

- **侧别与尺寸。** *现在*：标记落在它所属语言规定的一侧——横排中文在字下、横排日文在字上、竖排在列右侧
  （clreq §5.3.1、jlreq §3.3.9）——逐字居中，尺寸是约定的取值（1/4 em），而不是规范给出的数字。标记和下划线都会
  让行变高（行上下两侧的额外需求见 [`output-format.cn.md`](output-format.cn.md)）。*缺什么*：同一个字上同时有着重号
  和注音时，两者争的是同一块空间，而没有任何东西是为着重号预留的——标记本身在字的框外，而那条带是照注文量的。

## 书写模式

- **竖排。** *现在*：已经实现——列、列自己的行长、旋转的欧文 run、落在列侧的注音与着重号，以及由它们带出来的
  行高。*缺什么*：除了同一批约定为横排定义的规则之外，没有竖排专用的字距或字间调整；没有从右到左的列，因为
  `VerticalLr` 是被拒绝的，而不是被横排掉；也没有自动默认，因为想要列就得在请求里提出。

## 基线模型

- **句号在字框内的墨迹位置**（clreq §6.1.3、jlreq §3.1.2）。*现在*：画出来的就是字体字形自带的摆放。*缺什么*：
  它在 em 框内的语言相关位置没有被建模，因为这需要引擎不读取的字体变体。
- **基线种类。** *现在*：一行只有一种基线模型——已解析字体报出的 ascent 与 descent。*缺什么*：表意文字基线与
  字母基线没有被建模，原因相同：说明一个字符想要哪一种的变体没有被读取，所以两者都不作承诺。

## 文本效果与语法高亮

- *现在*：两者都原样透传——`TextEffectId` 指向使用者注册表里的一个效果，`SyntaxSpans` 给文本元素的分段着色。
  *缺什么*：两者都不参与塑形、度量或断行，而带效果绘制的文本走的是字符串路径，所以从文本绘制它的使用者会再塑形
  一遍。*绕过办法*：如果效果可以作用在已经塑形好的字形上，就把它作用到元素的字形 run 上；这样量出来的和画出来的
  是同一样东西。

## 从右到左的文本

- *现在*：已经排出来了——语言为从右到左的段落从右缘填充，每个 run 按自己的方向塑形，混排行里的各 run 被摆成
  视觉序，成对字符（括号、引号）画成镜像。级别与视觉序来自一份 UAX #9 实现；段落方向、行级规则与镜像则属于本
  组件。*缺什么*：没有把方向强加到某个区间上的 API——调用方无法像文档格式自带的 bidi override 那样说"这一段是
  从右到左"。*绕过办法*：让语言来携带方向（段落声明的语言决定它），或者切分文本，让段落把两个方向分开。

## 语言与未声明语言的文本

- *现在*：没有声明语言的段落按它自己的文字来读——带假名的文本按日文排、带谚文的按韩文排，无论请求为整份文档声明
  了什么，因为跟随语言走的一切（注音落在哪里、怎么排、断行、禁则、断词）否则会拿文档的约定去回答，而不是拿文本
  的约定。这个推断是**默认值**：声明过的语言永远优先。*缺什么*：纯汉字文本什么都不推断，因为简繁中文共用一套
  文字，所以没有声明又没有假名谚文的段落保持请求原样。*绕过办法*：凡是光看文字说不清的地方，就逐段声明语言。

## 文档一致性守则

本套文档是一起发布、一起维护的：

- **一页一题。** 每一页回答同一类问题——两份格式、设计、各语言、断行、摆放规则、绘制、服务器，以及本页列出的
  缺口——所以每一页都能单独读。整套文档的目录在总览页（[`README.cn.md`](README.cn.md)）上。
- **每一页都存在两份，结构相同。** 英文页与中文页的章节相同、顺序相同，所以一个章节要么两边都有、要么两边都没有，
  两版不会各自漂移。
- **链接只在这套文档之内。** 一页只链本组件的其它页，英文版链英文页、中文版链中文页，所以任何链接都不会把你带到
  你安装得到的文档之外。
- **单位和术语处处同义。** 长度是像素，`em` 只出现在约定以 em 给出量值的地方，而一个术语在任何一页上的含义，
  都与最先引入它的那一页相同。
- **缺口要么写在它该在的那一页，要么就列在这里。** 不会因为"读者大概不会注意到"而略过任何一条。

这些局限都是已知且写下来的，而不是默认为不存在。
